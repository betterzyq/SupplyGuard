# 人工验收与审计手册

## 操作边界
工作目录固定为 `/root/autodl-tmp/SupplyGuard`。不要执行 `make seed`、`build-graph --reset`、共享环境升级或全局进程清理。P1 不需启动其他两个项目，也不需要访问其目录。

## 第 1 阶段命令
以下入口由 P1 提供，实际运行结果见 `reports/phase-1.md`。

```bash
cd /root/autodl-tmp/SupplyGuard
make phase1-check
make acceptance-status
make acceptance-up
make phase1-smoke
make phase1-browser    # 可选：本机已准备的隔离 Chromium 浏览器检查
```

- `phase1-check`：离线 Python/API 测试、修改文件 lint、TypeScript 和隔离目录中的前端生产构建；不联网安装依赖。
- `acceptance-up`：检查本项目数据库配置，增量准备演示账号，再启动 `127.0.0.1:8100` API 与 `127.0.0.1:3100` 前端；端口占用则退出，不杀已有进程。
- `phase1-browser`：在运行 SupplyGuard 的服务器内，使用项目 `.local/` 的 Playwright 1.58.2 / Chromium 验证登录、场景联动、角色切换、管理页面拦截及两种视口，截图写入 `.local/acceptance/phase-1/`。这不检查你自己电脑到服务器的连接。浏览器和缺失运行库仅解包在项目内，未安装到系统；迁移服务器时需重新准备此可选工具。
- `phase1-smoke`：通过真实 HTTP 登录，校验两类角色、首页、场景切换和管理员边界；不运行付费 LLM。
- 若配置指向其他数据库、基础设施尚未运行或账号密码已有人工修改，命令给出失败原因；不会自动重启基础设施或重置密码。
- 验收用默认演示账号：`admin@example.com`、`enterprise@example.com`，默认密码 `password123`；仅本地演示环境使用。已存在账号的密码不会覆盖。
- 电脑访问远程 AutoDL 服务需要端口转发，详见下一节；不能把服务器内的 `localhost` 地址直接当成自己电脑已可访问的地址。

源代码变更后，先执行 `make acceptance-down`，再执行 `make acceptance-up`；启动器不会擅自重启已有进程。`phase1-check` 使用独立构建目录，不替换当前验收产物。

## 从自己的电脑访问 AutoDL

`acceptance-up`、`phase1-smoke` 和 `phase1-browser` 在 AutoDL 服务器运行。你电脑上的浏览器访问 `localhost` 时，连接的是你的电脑，不是 AutoDL。服务只监听服务器回环地址，需使用以下任一方式转发；仅转发前端 3100 即可，API 由前端同源代理访问。

### 方式一：VS Code Remote-SSH

1. 在已连接该 AutoDL 服务器的 VS Code 窗口中，打开底部“端口 / Ports”面板。找不到时，通过命令面板运行 `Ports: Focus on Ports View`。
2. 点击“转发端口 / Forward a Port”，输入 `3100`。
3. 点击该行的浏览器图标，或打开该行显示的“本地地址 / Local Address”。
4. 若显示本地 3101、4123 等其他端口，访问显示的地址；不要仍然访问 3100。保持 VS Code 的远程连接开启。

操作依据：[VS Code 官方端口转发说明](https://code.visualstudio.com/docs/remote/ssh#_forwarding-a-port-creating-ssh-tunnel)。

### 方式二：电脑本地 PowerShell / Terminal

在你自己电脑另开 PowerShell、Windows Terminal 或 macOS/Linux 终端。不要在当前提示符为 `root@autodl-container-...` 的远程终端、AutoDL 网页终端中执行。

从你现有的 AutoDL SSH 登录命令复制 SSH 端口、SSH 主机和用户名。下方 `SSH_PORT`、`SSH_HOST` 是待替换的占位符；若原登录命令使用密钥 `-i` 等选项，同样保留。

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:3100:127.0.0.1:3100 -p SSH_PORT root@SSH_HOST
```

SSH 端口不是网页端口 3100，也不是 API 端口 8100。`-N` 表示只转发，成功后没有远程 shell 提示符是正常现象。完成认证后保持此窗口开启，在电脑浏览器访问：

```text
http://127.0.0.1:3100/login
```

若提示 `Address already in use` 或无法监听本地 3100，不要关闭其他项目：只把 `-L` 中第一个端口换成 13100：

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:13100:127.0.0.1:3100 -p SSH_PORT root@SSH_HOST
```

此时浏览器访问 `http://127.0.0.1:13100/login`，远程服务仍使用 3100。退出时在该 SSH 转发窗口按 Ctrl+C，只结束这条隧道。

### 分清两处连通性

- 在服务器终端：`curl --noproxy '*' -I http://127.0.0.1:3100/login`，应返回 HTTP 200。根路径 `/` 返回跳转 307 也是正常的。
- 在电脑终端（完成转发后）：Windows 使用 `curl.exe --noproxy "*" -I http://127.0.0.1:3100/login`；macOS/Linux 使用 `curl --noproxy '*' -I http://127.0.0.1:3100/login`。改了本地端口时同步替换 URL。
- 若服务器可访问、电脑拒绝连接：检查端口转发窗口是否存活，以及浏览器使用的本地端口是否正确；不需要重新构建或重启数据库。
- 若 SSH 提示 `channel ... open failed: connect failed`：检查 SSH 连接的目标是否确实为运行 SupplyGuard 的同一实例，再在服务器检查 `make acceptance-status`。
