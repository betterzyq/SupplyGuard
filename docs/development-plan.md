# 分阶段开发与交付

## 执行原则
每阶段顺序：核对需求与影响 → 实现 → 自动测试 → 接口/浏览器验证 → 写实测报告 → 用户人工验收。用户明确通过后推进下一阶段；缺陷在当前阶段闭环。P1—P5已获用户人工验收通过；P6开发与自测已完成，等待最终人工验收。

不设凭空的精度承诺或未经测量的上线时间。每阶段产物包含变更列表、测试结果、运行命令、人工步骤、限制和回滚方法。

| 阶段 | 交付 | 前置 | 人工通过标准 |
|---|---|---|---|
| P1 | 需求文档、两类权限、业务首页/导航、演示数据契约、验收工具 | 已审批方向 | 两类账号可登录，业务数据可复算，管理员边界正确 |
| P2 | 嵌入式地图、风险图层、物流跟踪、时间回放 | P1 通过 | 地图/列表/详情一致，断网演示可操作 |
| P3 | 库存约束传播、替代方案、成本与缓冲比较 | P2 通过 | 修改参数改变结果，手算样例通过，金额不重复 |
| P4 | 公开数据管线、预测模型、旧评测修复、复现报告 | P3 通过 | 无泄漏协议可审计，基线与模型公平比较 |
| P5 | 任务处置、报告导出、数据导入、企业 API | P4 通过 | 导入与任务可持久化，隔离/重复请求/审计正确 |
| P6 | 全链路回归、性能、三场景演示、商业说明 | P5 通过 | 一次完成业务故事，证据与宣传口径一致 |

## 技术约定
- 保留 Next.js/React/FastAPI/PostgreSQL/Neo4j/Qdrant/Redis，不为改版整体重写。
- P1 采用版本化 JSON 演示域，业务 API 从同一数据生成；不往旧图谱写新数据，界面明确旧技术图谱与新演示数据的边界。
- P2 通过浏览器能力和打包兼容检查后引入 MapLibre/deck.gl；锁定版本，不使用未验证的 next 文档接口。
- P3 用明确的规则/仿真计算；LLM 解释证据，不承担金额和库存计算。
- P4 默认 CPU 小规模模型，数据许可和可获得性不通过时记录备选和阻塞，不伪造实验结果。
- P5 才将新增业务实体迁移为持久化模型；迁移有升级/降级、备份与隔离测试。
- 新旧评测策略须版本化，历史角色测试不得和新两类角色得分混合展示。

## 隔离与回滚
只使用本项目环境与命名空间。P1 不执行数据库迁移、重建演示数据或停止已有服务；验收进程使用专用端口。新增账号采用幂等增量方式，仅限 `demo-mfg` 租户，不改已有密码或岗位记录。

代码回滚以本阶段修改文件为单位，先保存人工变更，不使用 `git reset --hard`。P1 新演示数据是只读文件；不回滚或删除旧业务数据。关闭进程只能使用本项目验收启动器记录并核验的 PID。
